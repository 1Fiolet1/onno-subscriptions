# Разработка onno-subscriptions

Этот репозиторий — приложение учёта подписок клиентов на Onno Framework.
Основной источник бизнес-требований — оригинальное тестовое задание, предоставленное пользователем.
Разрабатывай запрошенный этап; установка скиллов сама по себе не означает переход к реализации всего приложения.

## Стек и область работы

- Java 21, Spring Boot 3.4.4, Gradle 8.14.4, Groovy DSL (`build.gradle`).
- Для приложения выбран PostgreSQL; подключение и запуск базы проверяются отдельно.
- Это потребитель опубликованных библиотек `su.onno`, а не исходный репозиторий фреймворка.
- Проверяй классы, методы и настройки по используемой версии Onno. Скиллы взяты из `main` и могут описывать API более новой версии, чем установленная библиотека.
- Работай в предоставленном пользователем проекте. Правила исходного репозитория Onno о PR, слиянии, публикации библиотек и его внутренних модулях не являются рабочим процессом этого приложения.

## Использование Onno Skills

Официальные скиллы установлены в `.agents/skills/`. Их источник и локальная адаптация описаны в [.agents/ONNO_SKILLS.md](.agents/ONNO_SKILLS.md).

Перед работой с Onno прочитай [.agents/skills/onno/SKILL.md](.agents/skills/onno/SKILL.md), затем подходящий специализированный скилл. Загружай только необходимые инструкции и справочные файлы.

## Правила реализации

- Описывай бизнес через Java-метамодель Onno: справочники, документы, табличные части, регистры, перечисления и типизированные ссылки.
- Используй генерируемые Onno схему, репозитории, API и формы. Добавляй собственные контроллеры, DTO и инфраструктуру только при обоснованной необходимости.
- Размещай UI-настройки в `EntityView`, `Layout` и `Page`; явно оформляй видимые сущности, меню, денежные суммы и даты.
- Для правил используй `Validated` и `BusinessRule`; для проведения — `Postable` и механизмы регистров.
- Проверяй реальную семантику сохранения, проведения, перепроведения и транзакций перед написанием бизнес-логики.
- Достаточность средств, отменённые подписки, расчёт срока по максимальной длительности строки и корректность движений должны иметь автоматизированные проверки.
- Реальные пароли, токены и локальные данные не включай в репозиторий.

## Проверка и общение

- После существенных изменений кода или конфигурации запускай `./gradlew clean build --no-daemon` либо подходящую более узкую проверку.
- Для изменений только инструкций проверяй скиллы и ссылки; повторная сборка приложения не требуется.
- Команды вида `:onno-framework:test`, `:onno-ui-starter:buildFrontend` и `publishToMavenLocal` относятся к разработке исходников фреймворка и не нужны для этого приложения без отдельной причины.
- Объясняй пользователю действия и результаты на русском. Отчитывайся о каждом действии: что изменено, что проверено, какой результат получен.
- Используй уже предоставленные требования; спрашивай о существенных неоднозначностях, которые нельзя разрешить по ТЗ и документации.
- Обновляй README при изменениях запуска и поведения приложения. Отделяй выполненные проверки от предположений.
- Публичный репозиторий, PR, issue и развёртывание создавай только при авторизации пользователя на соответствующее действие.
